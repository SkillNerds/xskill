# TaskAgent 轨迹拆分：当前"窗"机制说明 + 改进提案

> 状态：提案（discussion）。v0.6.0a6 已落地"窗"机制的止血修复（多窗循环 + 无 User 窗并入），
> 但窗机制本身偏丑陋，计划在 **0.6.0 正式版前**换掉。本文档供该重设计讨论用。
---

## 0. 背景：三个 agent 各自规避 LLM 上下文上限

server 端 LLM 的上下文（一次能读入的输入量）有限，而轨迹（trajectory）可能几万行、
上百万字符。三个 agent 各自有一套"别撑爆上下文"的办法：

| Agent | 作用 | 当前规避方式 |
| --- | --- | --- |
| **TaskAgent** | 把轨迹按用户意图切成 AtomTask | **窗**（本文档重点） |
| TaskClusterAgent | 把 atom 归类进 skill | （待梳理，本轮不展开） |
| EditAgent | 用 atom 改写/生成 skill | （待梳理，本轮不展开） |

本文档只聚焦 **TaskAgent 的拆分机制**；后两者标注为后议。

---

## 1. 当前机制：基于"窗"的拆分

### 1.1 什么是窗

**窗（window）= 从当前续接点（resume point）往后截出的、不超过 `max_context_chars`
（当前 30000 字符 ≈ 7500~9500 token）的一段轨迹原文。** 因为整条轨迹喂不进上下文，
只能用一个固定大小的"取景框"框住一段读。

- 续接点 `start_line` 来自 `store.last_offset(traj_id)`——上次拆到哪了。
- `_line_window()` 从续接点按整行累加字符，到 30000 上限即停（至少 1 行）。

### 1.2 拆分流程（v0.6.0a6 修复后）

`run()` 在一次调用内**循环逐窗推进**，直到续接点覆盖到文件末尾（EOF）：

1. 截当前窗 → 标注其中的 `## User` 行（带行号）。
2. 把这一窗喂给拆分 agent，agent 对每个用户意图调一次 `submit_atom(start_line, ...)`
   ——**只报起始行，不报结束行**。
3. 结束行由代码几何推导（`_derive_ranges`）：中间 atom 的 `offset_end` = 下一 atom 的
   `start_line`；一窗里最后一个 atom 的 `offset_end` = 窗口边界 `window_end_line`。
4. 落盘，续接点推进到本窗末尾，进入下一窗。

### 1.3 两个补丁（让循环不卡死）

- **无 `## User` 的窗**（一大段 assistant 输出/工具结果，没有新用户意图边界）：
  把它**并入上一个 atom 的区间**（延长 `offset_end` + 重算 `raw_segment`），推进续接点。
  这样循环能跨过去；内容不丢，但归到上一个意图里。
- **终止**：续接点到 EOF，或某窗未推进续接点（开头即无 User、无上一 atom 可并）即停。
  续接点严格递增且以总行数为上界 → 数学上必然有限步终止（已用真实大轨迹实测，无限循环
  硬上限从未触发）。

---

## 2. 当前机制的问题（为什么要换）

### 2.1 窗按字符硬切，与意图边界无关

窗在第 30000 个字符处截断，落点和"用户意图从哪结束"毫无关系。后果：

- **超窗意图被切在无意义位置**：一个"提问 + 超长执行"超过 30000 字符时，结构上**产不出
  比窗更大的 atom**——它必然被斩在窗口边界，且 agent 只读到这个意图的前 30000 字符就打标，
  写出的 intent/summary 是基于**残缺内容**的判断。

### 2.2 "无 User 窗并入上一原子"是 workaround

- 原子大小**极不均匀**：一个意图后面跟几窗 assistant 长输出，会全被吸进同一个 atom，
  `raw_segment` 可能上十万字符。
- **开头前言可能丢**：首个 `## User` 之前的内容若自身超过一个窗，没有上一 atom 可并，
  续接点卡住——这段（乃至其后）不进任何 atom。

### 2.3 token 浪费严重——拆分根本不需要看 assistant 正文

这是最关键的一点。真实数据（34727 行、约 154 万字符的轨迹）：

- 一次 `run` 实际跑了 **52 个窗**，其中 **25 个含 User、调 LLM**，每次喂 ~30000 字符
  （≈ 7500~9500 token）。
- 但窗里**绝大部分是 assistant 输出 / 工具结果**——而判断"用户意图从哪切换"**只需要看
  User 轮**。我们花了大量 token 把 assistant 正文反复喂给模型，模型却根本不靠它来定边界。

一句话：**当前机制为了"切"而读了大量"切"用不到的内容。**

---

## 3. 改进提案：只读 User 轮 + 行号拆分（弃用窗）

### 3.1 核心洞察

拆分的唯一职责是**找用户意图边界**。而意图切换是**由用户发起的**——边界永远落在某个
`## User` 行上（`submit_atom` 本来就强制 `start_line` 必须是 `## User` 行）。

**所以拆分根本不需要 assistant 正文。** 把 assistant/工具内容从喂给 agent 的 prompt 里
剥掉，只保留**带行号的 User 轮**，agent 看着这串用户提问就能决定怎么切、输出 `start_line`。

### 3.2 新方案

喂给拆分 agent 的内容（示意）：

```
SYSP（系统提示）
[line:5]   ## User  Deploy xquiz to 1717.
[line:31]  ## User  Now redesign the frontend.
[line:88]  ## User  Add tests.
...（整条轨迹的所有 User 轮，各带行号，assistant 正文一律省略/折叠）
```

agent 据此对每个意图调 `submit_atom(start_line)`；结束行仍由代码几何推导（不变）。

### 3.3 为什么这样就**不需要窗了**

User 轮通常只占全文很小一部分。还是那条 154 万字符的轨迹：若只留 User 轮 + 行号，
体量大概率**一次就能装进一个上下文**——于是：

- **免窗**：整条一次读完，没有 30000 字符截断。
- **免吸收**：assistant 长输出本来就不在 prompt 里，不存在"无 User 窗"，workaround 消失。
- **免残缺打标**：agent 看到的是**全部** User 轮的全局视图，不再只见局部一窗。
- **省 token**：从"25 次 × ~8k token"降到"1 次 × User 轮体量"，量级下降。
- **意图边界天然对齐**：边界本就落在 User 行，几何推导出的区间不再被窗口边界污染。

### 3.4 对用户原提案的评估（逐条）

用户笔记原话：「TaskAgent 仅仅负责输出 offset？读取内容类似 SYSP + User + Ass +
User2(line num) + User3(line num)，通过观看 user 的部分来进行拆分？」

- ✅ **"仅输出 offset"** —— 对，且**现状已经如此**（`submit_atom` 只收 `start_line`，
  结束行代码推）。这条不用改，正好印证方向。
- ✅ **"只看 User 部分拆"** —— 对，是本提案的核心。补充量化依据：见 §2.3 / §3.3 的 token 账。
- ⚠️ **一个边角**：偶有意图边界需要一点 assistant 上下文才好判断（比如用户只回了"continue"，
  得看上一轮 assistant 在做什么）。可保留**每轮一条极短摘要/首行**而非整段正文，成本极低。
- ⚠️ **单条 User 轮超长**：极少见（用户粘贴超大输入）。可对**单个 User 轮**做截断而非整体窗化，
  退化代价远小于现在。

### 3.5 待定 / 风险

- `intent`/`summary` 的质量：现在 agent 能看到 assistant 正文来写复盘，剥掉后 summary 可能变弱。
  缓解：summary 可以延后到 cluster/score 阶段、用 `raw_segment`（仍是全文）补，而不是在拆分时写。
  ——**这是这套方案最需要先验证的一点**。
- `readfile` 工具仍在：agent 需要某段 assistant 细节时可按行号自己 `readfile` 取，按需而非全量。
