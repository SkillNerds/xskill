## 环境和范围

自动化使用提交导出的源码、独立的测试状态和模拟模型。Windows 使用 Python 3.12.10，另在 Ubuntu WSL 补测。真实测试在同一台 Windows 机器运行，使用独立的 XSkill 状态目录、技能库、合成轨迹、SQLite 和本地 Git 仓库。新建和更新的目标均为 `gate-feishu-debug`，另设非目标技能 `gate-unrelated`。

真实模型使用 `gpt-5-nano` 和 `text-embedding-3-small`。两版的模型接入源码相同，测试通过同一份已有的本地 nano 兼容层发请求。测试配置关闭说明优化和任务图，以聚焦蒸馏与交付。首次真实测试因环境缺少 `tqdm` 在向量索引阶段停滞，将依赖补到临时目录后，索引恢复。合成轨迹之外，只读取已有模型配置来建立连接。

## 同模型同素材对照

从真实编辑入口开始，各版本在新建和更新场景各调度一次编辑。各场景使用相同的轨迹和 Atom 文件字节、候选分数，以及相同的初始技能内容。更新从相同的 `main` 文件树和同样的测试反馈开始。旧版走原有编辑流程，新版使用 `create_one` 或 `update_only`。这个对照固定了素材筛选结果。

| 场景 | 旧版 `aeee7c1` | 新版 `b2435f2` |
| --- | --- | --- |
| 新建，9 + 9 + 9 = 27 | 模型以单条未到 10 分为由拒绝写入。3 条全部保留在候选池，只有初始 `baby`（`973842c34503`）。 | 3 条素材全部提交到 `baby`（`246ffe0b6d9c`），正文却引用了未交付的脚本。修复回合后该引用仍未通过校验，运行标记为 `failed`，没有 `main`。 |
| 更新，9 + 8 + 9 = 26 | 生成 `staging`（`f32dfc0a91d2`），3 条素材全部消费，本轮没有生成自检脚本。 | 模型把门槛误读成单条至少 10 分，3 条素材仍在候选池，没有 `staging`。 |

输入指纹为相对路径和文件内容的 SHA-256 汇总。新建为 `041b7bd22591fe5bf13527f976bf0802f53026470d6eb1173d8ff35fb4f145bf`，更新为 `b9a0d58bea7cffa16afd573630dbcdfef28b5a3ec564de28b518481d83e947b8`。旧版两次编辑完成后，临时测试脚本在关闭阶段传入了旧版不支持的 `wait` 参数。表中结果通过编辑日志、候选文件和实际 Git 引用重新核实。

两次对照更新均未自然生成上次的占位脚本。另将真实 CLI 产出的同一份已知有问题的文件树原样送进旧版灰度提交入口。旧版接受并生成了 `staging`（`96ca37bdcdfa`）。从该提交取出的脚本，对合成无效 token 和虚假 scope 仍输出 `OK`、返回 `0`。旧版实际物化的灰度目录只包含 `SKILL.md`。这证明旧版会放行同一个有问题的产物，生成该脚本的概率未在本轮测量。

## 原因和结论

- **累计门槛误读。** 两版代码均按总分决定是否启动编辑。提示词和逐项评分进入模型后，模型有时会自行按单条分数重新判断，导致编辑已启动却没有写入或提交。真实 CLI 的后续编辑还出现了不合法的 YAML 文件头，程序按既有规则拒绝写入。旧版新建和新版更新的对照均直接复现了门槛误读。[候选计分](../../src/xskill/skill/candidates.py#L340) · [编辑流程](../../src/xskill/agents/skill_edit_agent.py#L554)
- **脚本存在和脚本可用是两个验收项。** 新版静态校验能检查正文、文件引用和实际提交。实测脚本仅判断第一个位置参数是否非空，按正文格式调用时甚至把 `--token` 当成 token，随后输出成功。脚本没有验证凭据或权限，因此即使 Git 与灰度链路正常，产物功能仍不合格。旧版直接接受同一产物，确认这一缺口早于指定蒸馏改动。[产物校验](../../src/xskill/skill/artifact_validation.py#L218)

指定范围的写入隔离、错误拒绝、重启恢复及切回默认模式已有通过证据。完整真实产物交付仍有失败。尚未验证的项目包括同一个真实产物从新建晋升后继续更新、真实飞书场景的技能效果以及公开基准分数。
