# xskill 推荐效果测评设计

日期：2026-08-21

对照代码：GitHub `origin/main`（本文按 2026-08-21 的 `70e97aa` 核对过发清单、埋点和 side 决策）。

这份文档说明怎么评「服务器发给用户的那份 skill 清单好不好用」。读者懂 xskill 和 Agent，不必先读推荐代码。先看第一章，知道我们在评什么；再按章节查某个数怎么算。

测评评的是清单发出去之后的效果，不是 SKILL.md 写得好不好，也不是轨迹被切成 atom 切得对不对。SkillEdit 改完一篇 skill、或 TaskCluster 把一段 atom 归进某个 skill，都不立刻开评。要等清单先发到用户手里，再等他之后又用了一段时间。

---

## 1. 我们在评什么

客户端会定期向服务器要一份「这个人该装哪些 skill」。一份最多大约 100 个 slot，按顺序拼成三段：

- pinned：prefs 里钉住的 skill，先占位子，不参与后面两段的排序。
- ranked，默认大约 80 个。从本仓库里已经有 main 的 skill 中，按全团队 main 近 30 天 UX 均分排序（并列看 use_count），再切前若干个。skillhub 不进这一段。目标是：别把 UX 很差的自研 skill 推到每个人机器上。
- recommended，默认大约 20 个。后台按这个人的兴趣方向，在 skill description 向量里找近邻，提前算好一列名字；取清单时再去掉已经在 pinned 或 ranked 里的，空出来的位子用 ranked 排序往后接着取。目标是：多给他一些 ranked 不一定排得靠前、但跟他手头事相关的 skill。

recommended 其实对过两份名字，不要当成同一份。一份是后台按兴趣提前算好的那列名字；另一份是用户这次实际拿到的那 20 个。取清单时会先丢掉已经出现在 pinned 或 ranked 里的名字，空出来的位子用 ranked 往后接着补。还没画出兴趣、或那列是空的，这 20 个就整段都是 ranked 接着往下取。所以用户手里的 recommended 常常是「兴趣命中去掉与 ranked 的重叠」再加「质量榜往后的」。评兴趣准不准时，对着后台按兴趣算好的那列；评用户真实拿到的时，对着他这次实际拿到的那 20 个，并标出其中有多少是后面补上的。

pinned、blocked、retired 不是算法选的。算 ranked 或 recommended 的命中率时，不要把它们算进「算法发出去的槽」。blocked 和 retired 根本不会发；pinned 会发，但不算进这两段的算法分母。

成功的统一定义是：某个 skill 先出现在他某次取到的清单里，从那一刻起算，在约定的观察窗口内，他后来的新 atom 的 used_skills 里第一次出现这个 skill。窗口报两档：发出去之后 7 天，以及发出去之后 30 天。发出去之前他就在用的，不算这次的成功。

数据从三处来，两段名单的取法不一样：

- recommended 的「谁、哪个 skill、side、sha、什么时候发的」，读清单埋点。现行代码只把 recommended 写进这张表，不写 ranked，也不写 pinned。同一行的去重键是 `(client_id, skill, side, sha)`：换了 side 或 sha 会再记一行，不是「一个人一个 skill 只留最早一次」。看「这个 skill 第一次发到他手上」时，按 `(client_id, skill)` 取最早时间；按 main 和 staging 切开时，按 side（必要时再加 sha）看，不要先压成一行。
- ranked 的名单现行埋点里没有。回放时按当时本仓库可分发集合、这个人的 pinned 与 blocked、retired，用同一套 main 近 30 天 UX 序把 ranked 重算出来。
- 他之后每个 atom 里，Agent 实际用过的 used_skills，以及用完之后打的 UX（1 到 10）。

后面例子里，为了能心算，把 ranked 缩成 3 个、把 recommended 缩成 2 个。除法怎么做和真系统完全一样，只是槽少。

三人在同一天取到清单（下面假设都没有 pinned）：

- 甲：ranked 顺序是 A、B、C，recommended 顺序是 D、E。取清单之前只用过 A。之后 7 天里用了 B（UX 8）、用了两次 D（UX 7 和 6）、还用了两份名单和 pinned 都没有的 X。
- 乙：ranked 也是 A、B、C，recommended 是 F、G。之后只用了 A（UX 9）。
- 丙：还画不出兴趣，recommended 那 2 个是 ranked 接着往下取的 D、H。之后什么都没用。

## 2. 怎么切开看，避免把不同事情糊成一个数

### 2.1 main 和 staging

同一份名单里，有的 skill 发的是 main，有的发的是 staging。先选定 skill 名字，再决定 side。skillhub 没有 staging，side 恒为 main。

这不是两套选人办法在对比，而是同一份名字下发了不同正文。只把「用了没有、用了会不会再来、用完 UX、相对 ranked 多出来的命中」按 main 和 staging 分开报。这样不会把「人找对了但 staging 写得差」算成推荐失败，也不会把「staging 碰巧好用」算成兴趣选得准。

现行取清单时，只要该 skill 有 staging，side 大致分三种来源：普通用户走有状态的 CanaryRouter（按人按 skill 粘住，避免小团队把 staging 饿死）；纳入或生成发起人、以及用量最多的用户走按体验分补漏换侧；prefs 还可以强行指定某个 skill 的 side。自动换侧和强制指定会让一部分人系统性地拿到另一面。按 main 和 staging 切开时，把这两类用户标出来单独报，不要和普通粘住分流混成一个数。

名单里有哪些名字、排得靠不靠前、人与人差多少，评的是名字，主表不按 side 拆。最多附一眼：这 20 个名字里当时有多少被标成 staging。

### 2.2 自研 skill 和 skillhub

ranked 只从本仓库 `SkillRepo` 里已有 main 的 skill 切，skillhub 不进 ranked。所以 ranked 那一支不用再按来源拆。某个 skillhub 内容后来被拷进本仓库、有了 main，会作为自研 skill 进 ranked，那时它已经不是 skillhub 源。

recommended 里两种都可能出现。采用、相对 ranked 多出来的命中、多少个槽被用到、用户新使用有多少落在这 20 个里、20 个里有没有至少打中一个、排得靠不靠前、新 skill 多不多、覆盖了全库多少 skill，这些要按来源各报一遍，再加一张合计。否则「skillhub 好不好找」和「自研 skill 选得准不准」会糊成一个数。

### 2.3 按兴趣选的，UX 整段顶上的，以及兴趣名单被 UX 补过的

recommended 要能分成三种来源，不要糊成一张主表：

- 后台按兴趣算好了一列名字，取清单时也主要用了这列（和 ranked 重叠后所剩仍够填满，或只补了很少）。
- 当时画不出兴趣、或那列是空的，整段 recommended 都是 ranked 接着往下取。丙进这一刀。
- 有按兴趣算好的名字，但去掉与 ranked 重名的之后不够 20 个，空位用 UX 尾部补。用户实际拿到的是两段拼出来的。

主表只看第一种里「真正来自按兴趣算好的那列」的那些名字。评用户真实拿到的效果时，用他这次实际拿到的整段 recommended，并写清其中兴趣命中和后面补上的各占多少。

### 2.4 人有的天天用，有的一周才用一次

甲窗口里用 3 次、3 次都在清单里；乙用 20 次、只中 5 次。按次数加总是 (3+5) 除以 (3+20)，大约 0.35，乙把总分按下去。按人平均是 1.0 和 0.25 再平均，得到 0.625，甲把总分拉上去。只比命中个数，乙是 5、甲是 3，乙显得更好，但乙其实更不准。

三种加法评的是三件事。规定如下：

- 同时报「按人平均」和「按次平均」。按人平均是每个人先算自己的比率再平均，评的是「对每个用户好不好」。按次平均是把所有发出去的次数、所有用了的次数加总再除，评的是「全网堆起来好不好」。主结论看按人平均。按次平均只当对照：用来发现「用得很多的人是不是其实推得很差」。
- 再按窗口内新用到的 skill 个数分成三层：少（1 到 3）、中（4 到 10）、多（10 以上）。每层自己做按人平均。阈值写死，不要看完数再改。甲、乙会进不同层，不会互相稀释。
- 每一档写清进了多少人、因为窗口内完全没有新使用而被放下的有多少人。没有新使用的人，不进「按人平均」（避免用空分母制造假稳定），但人数要写出来。
- 7 天那一档更容易只剩下天天用的人；一周用一次的人常常在 7 天里什么都还没用，会被放下。30 天档对这种人更公平。两档都报，解释时写清这一档剩了谁。
- 命中次数只做分子，不做「谁更好」的排名依据。

## 3. 多久评一次

服务器会定时根据新 atom 更新每个人的兴趣，并提前算好一列 recommended 名字。用户来取清单时直接读算好的结果，再去掉已在 pinned 或 ranked 里的，不够就用 UX 尾部补。兴趣变了、skill description 变了、有人 block 或 pin 了某个 skill，后台会把名单标脏再重算。这是「名单什么时候更新」，不是「效果什么时候评」。

效果必须等观察窗口到点。比较稳的做法是按队列滚动：每天或每周跑一次，只评「首次写进清单已经满 7 天」的人算 7 天档，只评「满 30 天」的人算 30 天档。刚发下去就评，采用率几乎一定是 0，没有意义。recommended 的「首次写进」可以看埋点；ranked 的「首次发出」看重算出来的那份名单对应的取清单时间。

TaskCluster 把 atom 归进某个 skill、或 SkillEdit 改完一篇 SKILL.md，都不触发效果测评。正文改了最多让 description 变了、过一阵名单跟着变，那是更新名单，仍要再等窗口。

「现在有多少人还画不出兴趣、有多少人还在拿上一份过期名单」这类健康情况，可以跟着后台更新一起看，甚至可以勤看。那是在看算名单的活有没有跟上，不是在看推得准不准。

评的时候分三条路，不要合成一个分数：

- 回放当时真正发给用户的清单，对照他之后的使用。recommended 可以读埋点；ranked 和 pinned 要按当时可分发集合、prefs、UX 序重算。评的是用户真实拿到的东西（包括过期名单、UX 补位、staging、强制 side）。
- 用当时已经有的 atom，按现在的选法重算「那天兴趣名单该是哪 20 个」，再对照之后的使用。评的是选人办法本身，方便和「随机 20 个」「ranked 接着往下的 20 个」对比。这一路不要混进取清单时的 UX 补位。
- 用三五个假用户验除法有没有写错。这测的是评测脚本，不是推荐效果。

## 4. ranked 要报的指标

这支指标回答的是：按 UX 排出来的这张全员榜，在扣掉这个人的 pinned、blocked、retired 之后，有没有把大家后来真会用的 skill 罩住、排得靠不靠前。不是在评「给这个人找得准不准」。

ranked 不是严格人人一份。pinned 先占位，余量不够时 ranked 配额会被压缩，recommended 甚至可以变成 0；各人的 blocked 也不同。只有几乎没人 pin、也没人 block 时，不同人的 ranked 才会高度重合。

回放 ranked 不要读现行埋点，按第一章的办法用 UX 序重算。

### 4.1 采用率（Adoption）

定义：某个 skill 先写进这个人的 ranked，从对应那次取清单的时间起，在窗口内他后来的 atom 的 used_skills 里第一次出现它，这一对「人与 skill」算采用。采用率是采用了多少对，除以 ranked 上发出去多少对。

怎么算：按人平均，是每个人「自己 ranked 上被用到的个数 ÷ 自己 ranked 上发出去的个数」，再对进这一档的人取平均。按次平均，是所有人的采用对数加总，除以所有人发出去的对数加总。7 天、30 天各算一遍。main 和 staging 分开报；自动换侧和 prefs 强制指定的用户单独成列。

为什么要有、作用是什么：先回答「榜上的 skill 有没有人用」。榜再好看，发出去没人用，ranked 就没有完成「把能用的 skill 发到手上」这件事。

测的是哪部分能力：ranked 的「发得出去、用得起来」，不是 recommended 准不准。

例子：甲的 ranked 是 A、B、C。A 在取清单之前就用过，窗口里没有「第一次出现」，不采用。B 窗口里新出现，采用。C 没用。甲的采用率是 1 除以 3。乙若窗口里才第一次用 A，也是 1 除以 3。丙三个都没用，是 0。按次平均是 (1+1+0) 除以 9。按人平均时丙没有新使用，不进平均，甲和乙都是约 0.33。

### 4.2 复用（Repeat）

定义：已经算采用之后，同一窗口里还有没有第二次用到这个 skill。

怎么算：有复用的采用对，除以采用对。按人、按次都报。main 和 staging 分开。

为什么要有、作用是什么：采用只说明「用过一次」。有人装上点一下就再也不碰。复用用来区分「试了一下」和「形成习惯」。

测的是哪部分能力：ranked 发出去的 skill 有没有留存，不只是有没有被点到。

例子：甲的 ranked 里只有 B 算采用，B 只用了一次，复用是 0。D 用了两次，但 D 不在 ranked，不算在这支。

### 4.3 体验（UX）

定义：每个采用对，取这个人在窗口内每次给这个 skill 打的 UX，先对这个人这个 skill 取平均，再对所有采用对取平均。

怎么算：缺分的使用不要当成 0 分，从分母拿掉并写清拿掉了几条。main 和 staging 分开。自动换侧用户单独报。

为什么要有、作用是什么：采用把「用了 UX 很差」也算成功。UX 用来看用了之后好不好用。ranked 本身就是按 UX 排的，这里是在验证：榜上的 skill 发出去以后，这个人自己打的分是不是也高。

测的是哪部分能力：ranked 选「用着不差的 skill」这件事，在发出去之后是否兑现。

例子：甲的 B 打了 8，乙的 A 打了 9，两人平均 8.5。

### 4.4 槽位命中率（Slot Hit）

定义：这个人 ranked 那几个位子里，窗口内被用过的 skill 个数，除以实际发出去的 ranked 槽数（pinned、blocked、retired 先拿掉）。

怎么算：每个人先算自己的比率，再按人平均；也可以按次把分子分母加总。和采用率的差别是：采用率分母是「发出去的人与 skill 对」（同一 skill 对多人算多对），槽位命中是「这一份名单里有多大比例的位子不是空枪」。

为什么要有、作用是什么：采用率高也可能是「只推了很少几个、但那几个全中」。槽位命中看整份榜是稀疏空枪，还是多数位子有人接。

测的是哪部分能力：ranked 整份名单的利用率。

例子：甲 3 个位子用了 B，命中 1 除以 3。若 3 个里有 1 个其实是 pinned，它根本不应出现在 ranked 分母里。

### 4.5 使用归因率（Attribution）

定义：这个人窗口内新用到的 skill 里，有多少本来就在他当时的 ranked 上。分子是「新使用 ∩ ranked」，分母是他窗口内新使用的 skill 个数（发出去之前用过的要先减去）。

怎么算：按人算再平均。分母是「他新用了什么」，不是「我们发了什么」。即使用了不少清单外 skill，分母也不为 0。

为什么要有、作用是什么：采用率看「发出去的有没有被用」。归因率反过来看「他真正用的，有多少被榜罩住了」。两个方向都要，否则只知道空枪多少，不知道漏了多少。

测的是哪部分能力：ranked 对真实使用的覆盖，从用户行为往回看。

例子：甲新使用是 B、D、X，共 3 个；落在 ranked 的只有 B，归因率 1 除以 3。

### 4.6 清单外比例（OOL）

定义：窗口内新使用里，pinned、ranked、recommended 三份都没有的比例。分子是三份都罩不住的新 skill 个数，分母是新使用个数。

怎么算：ranked 和 recommended 两边报同一个数。读成「算法两段加上钉住的都没罩住」。用了 pinned 的 skill 不算漏推。

为什么要有、作用是什么：有人用的 skill 三份都没发，说明该发的没发。只看命中会以为「发出去的都挺准」，看不见漏推。若把 pinned 也算进漏推，钉住且被使用的 skill 会把 OOL 抬高，那是控制面意图，不是算法漏了。

测的是哪部分能力：下发清单合在一起的漏推，不是某一段内部排得准不准。

例子：甲的 X 三份都没有，3 个里漏了 1 个，比例是 1 除以 3。若甲还用了自己 pin 的 P，P 不算进这 1 个。

### 4.7 前 k 名罩住了多少后来会用的（R@k）

定义：把重算出来的 ranked 当成有顺序的名单。看这个人窗口内新使用的 skill，有多少出现在名单的前 k 名。比率是「新使用 ∩ 前 k 名」的个数，除以新使用个数。k 取 1、3、5、20，分别记为 R@1、R@3、R@5、R@20。真系统 ranked 默认大约 80 个，R@20 就是榜的前四分之一。

怎么算：每个人先算自己的比率，再按人平均。新使用为空的人跳过，并报参与人数。读法是「全员 UX 序能不能把真会用的排到前面」，不是「给这个人排得准」。顺序必须来自当时的 UX 重算，不能从现行埋点里读（那里没有 ranked）。

为什么要有、作用是什么：采用率不看顺序。同样罩住 1 个，排在第 1 名和第 80 名，对「榜排得对不对」不是一回事。这个数看排序本身。

测的是哪部分能力：ranked 按 UX 排序的质量。

例子：甲新使用是 B、D、X。ranked 顺序 A、B、C。R@1：前 1 名是 A，一个都没罩住，是 0。R@3：前 3 名罩住 B，是 1 除以 3。

### 4.8 不同人 ranked 有多像（Jaccard）

定义：两个人 ranked 集合的 Jaccard = 交集个数 ÷ 并集个数，再对所有人对取平均。

怎么算：只比名字集合，不比顺序。几乎没人 pin、也没人 block 时，这个数应接近 1，用来检查「质量榜还是不是公共的」。有控制面偏好的团队里，Jaccard 明显小于 1 是预期现象，先按「是否有 pinned 或 blocked」分层，不要先当成个性化很好。

为什么要有、作用是什么：看 ranked 有没有被 prefs 打散。接近 1 不表示效果好，只表示这支名单在没有偏好时仍是全员同一张质量榜。

测的是哪部分能力：ranked 作为公共质量榜的稳定程度。

例子：甲和乙都没有 pin，都是 A、B、C，Jaccard 是 1。若乙 pin 走了 A，乙的 ranked 变成 B、C 再往后补一个，两人 Jaccard 就会小于 1。

## 5. recommended 要报的指标

这支回答：按这个人最近在干什么选的那一列名字，有没有被用、有没有比 ranked 多推对东西、顺序对不对、是在推新东西还是在回放旧 skill。

指标能对两份名单各算一遍时，都要算：后台按兴趣算好的那列名字（评兴趣选得准不准），以及用户这次实际拿到的 recommended（评他手里那 20 个好不好用）。主表谈「兴趣准不准」时，只用按兴趣算好的那列里、且当时不在 ranked 或 pinned 里的那些名字。用户实际拿到的若掺了后面补上的位子，R@k、MRR、MAP、NDCG 不要把补上的那一段当成兴趣排序。

### 5.1 采用率（Adoption）

定义、算法与 ranked 相同，只是只看写进 recommended 的那些。这份可以从埋点回放。main 和 staging 分开；skillhub 和自研分开再加合计。自动换侧和强制指定单独成列。

为什么要有、作用是什么：先回答「recommended 里发出去的 skill 有没有人用」。这是这一段最直接的效果。

测的是哪部分能力：recommended 槽「发得出去、用得起来」。若要回答「兴趣找得准不准」，只统计用户实际拿到的里面、来自按兴趣算好的那列的那些。

例子：甲的 D、E，D 窗口里用了，E 没有，采用率 1 除以 2。乙的 F、G 都没用，是 0。丙是整段 UX 顶上，不进兴趣主表。

### 5.2 相对 ranked 多出来的命中（Incremental Hit）

定义：已经算 recommended 采用，而且这个 skill 当时不在他的 ranked 里，也不在 pinned 里。

怎么算：报两个数。一个是「多出来的采用对 ÷ recommended 发出去的对」，偏严。一个是「多出来的采用对 ÷ recommended 采用对」，看采用里有多少是 ranked 给不了的。main 和 staging 分开，skillhub 和自研分开。

为什么要有、作用是什么：recommended 存在的理由，就是补 ranked 罩不住的。没有这一条，recommended 里很多「采用」其实只是「UX 榜接着往下的热门货」，不是兴趣找对人。

测的是哪部分能力：recommended 相对 ranked 的增量价值。这是 20 个位子值不值得留的主依据。若命中来自后面补上的位子、而不是按兴趣算好的那列，要另外计数，不要算进「兴趣增量」。

例子：甲的 D 不在 ranked 里，算多出来的命中。若有人 recommended 里给了 B、而 B 已在 ranked，采用了也不算多出来的（取清单时 B 本来就会被跳过）。

### 5.3 复用（Repeat）

与 ranked 复用相同，换 recommended 那一支。甲的 D 用了两次，复用是 1。用来看 recommended 推出去的 skill 会不会留下。

### 5.4 体验（UX）

与 ranked 的 UX 相同，换 recommended 那一支。甲的 D 两次是 7 和 6，平均 6.5。用来看推出去的 skill 用着好不好。若采用高、UX 低，是人找对了但 SKILL.md 不行，或 staging 不行（看 side 切开）。

### 5.5 槽位命中率（Slot Hit）

定义：用户实际拿到的 recommended 位子里，窗口内被用过的个数 ÷ 实际发出去的 recommended 槽数。

为什么要有、作用是什么：看整份 recommended 是空枪还是有人接。和采用率一起：采用率看「发出去的对」，槽位命中看「这一份里用了几个」。

测的是哪部分能力：recommended 整份名单的利用率。有人 pin 很多导致 recommended 槽变成 0 时，这个人跳过，不要用 0 当空枪。

例子：甲 2 个位子用了 D，是 1 除以 2。

### 5.6 使用归因率（Attribution）

定义：窗口内新使用里，落在他当时实际拿到的 recommended 中的比例。

为什么要有、作用是什么：从用户真实使用往回看，有多少是这 20 个罩住的。和 ranked 归因、pinned 对照：使用是主要落在哪一段。

测的是哪部分能力：recommended 对真实使用的覆盖。

例子：甲 3 个新使用里有 D，归因率 1 除以 3。乙的 A 不在 recommended 里，是 0。

### 5.7 清单外比例（OOL）

与第 4.6 节同一个数（三份都没有才算漏）。这边读成「recommended 也没罩住」。

### 5.8 对照：随机 20 个，以及 ranked 接着往下的 20 个（Baseline）

定义：对每个当时画得出兴趣的人，用同一时刻能下发的全部 skill（本仓库可分发，加上当时启用的 skillhub），随机抽 20 个算一遍采用、有没有至少打中一个、多出来的命中；再用当时 UX 序在扣掉 pinned 和 ranked 之后的下 20 名再算一遍。随机要固定种子，重复多次取平均。

为什么要有、作用是什么：没有对照，0.3 的采用率不知道算好还是算差。打不过随机，说明兴趣检索没有信息。打不过「ranked 接着往下取」，说明按兴趣算好的那列还不如取清单时往后补的办法。

测的是哪部分能力：兴趣检索相对朴素办法有没有增益。只适合对按兴趣算好的那列做；不要拿已经掺了后面补位的、用户实际拿到的名单，再和「UX 下 20 名」比，那是自己和自己比。

### 5.9 前 k 名罩住了多少后来会用的（R@k）

定义：把名单当成有顺序的列表。新使用里有多少出现在前 k 名。每个人先算，再按人平均。k 取 1、3、5、20。

怎么算：分母仍是窗口内新使用个数。列表短于 k 时，k 封顶到列表长度。skillhub 和自研可分开报，主表用合计。兴趣检索的 R@k 用按兴趣算好的那列的顺序。评用户手里好不好用时，用他实际拿到的顺序，但要写清前面有多少是后面补上的。

后台按兴趣填那列名字时，按兴趣中心依次搜，第一个中心就能把 20 个填满，不是「每中心每轮只取 1 个」。列表顺序不是单一分数从高到低排到底。R@1、R@3 仍然有用，但不要解释成教科书里那种标准排序器。更稳的是：有顺序的 R@k 当主报之一，同时报下面的 Hit@20。

为什么要有、作用是什么：采用不看顺序。前面几个准不准，决定用户先看到的是不是真会用的。

测的是哪部分能力：按兴趣算好的那列（或用户实际拿到的名单）排序靠前的准不准。

例子：甲新使用是 B、D、X，按兴趣算好的顺序是 D、E。R@1：前 1 名 D 命中，是 1 除以 3。

### 5.10 第一个命中有多靠前（MRR）

定义：从名单左边往右看，第一个「后来真用了」的 skill 排在第几名，取倒数。第 1 名就是 1，第 2 名就是 0.5，一个都没有就是 0。再对按人平均。

为什么要有、作用是什么：R@k 看的是整截前缀罩住多少。MRR 只关心「用户要看几个才会碰到一个真会用的」，对「第一个就该准」更敏感。

测的是哪部分能力：列表头部准不准。兴趣主表用按兴趣算好的那列。

例子：甲第一个命中是第 1 名，MRR 贡献 1。乙一个没有，贡献 0。有新使用的两个人平均 0.5。

### 5.11 多个命中是不是都靠前（MAP）

定义：每命中一次，记下「到这个位置为止已经命中几个 ÷ 当前位置」，再对这些命中位置取平均，得到这个人的平均精度。再对所有人取平均。

为什么要有、作用是什么：有的名单第一个很准、后面全错；有的是命中散在整份列表里。MAP 要求多个命中整体靠前，不只看第一个。

测的是哪部分能力：整份有序列表的排序质量。兴趣主表用按兴趣算好的那列。

例子：甲只在第 1 名命中 D，第 2 名 E 没用，平均精度是 1。乙是 0。MAP 为 0.5。

### 5.12 排在前面的，用起来分够不够高（NDCG）

定义：没用过当 0，用过则把窗口内 UX 均分当成「有多相关」。按位置加权求和（越靠前权重越大），再除以「按 UX 从高到低理想排列」时的同样加权和。得到 0 到 1 之间的数。每个人先算自己的，再按人平均。窗口内新使用为空的人跳过，不记成 0。

位置折扣：第 i 名（从 1 起）的贡献是相关度除以 log2(i+1)。第 1 名 log2(2)=1，权重最满；第 2 名约 0.63；第 3 名是 0.5，越往后越轻。实际顺序的加权和叫 DCG，理想顺序的加权和叫 IDCG，NDCG = DCG 除以 IDCG。

为什么要有、作用是什么：采用、Hit@20 只问集合里有没有用过；R@k、MRR、MAP 只问用过的排得靠不靠前，把用过一律当 1。NDCG 多一层：同样是用过，UX 更高的应更靠前。采用高但前面都是 UX 3 分的 skill，NDCG 会很难看。

测的是哪部分能力：排序有没有同时照顾「会用」和「用着好」。兴趣主表用按兴趣算好的那列，不要把后面补进去的槽当成兴趣排序。

例子：甲按兴趣算好的顺序是 D、E、F、G。窗口里 D 用过、UX 均分 6.5，E 没用，F 用过、UX 9，G 没用。相关度是 6.5、0、9、0。实际顺序的 DCG：第 1 名 D 贡献 6.5，第 2 名 E 贡献 0，第 3 名 F 贡献 9 除以 2 等于 4.5，第 4 名 G 贡献 0，DCG=11。理想顺序应把 9 分的 F 放第 1、6.5 分的 D 放第 2：第 1 名 9，第 2 名 6.5 除以 log2(3) 约等于 4.10，IDCG 约 13.10。甲的 NDCG 约 11 除以 13.10 约等于 0.84。两个会用的都在名单里，Hit@20 看起来不错，但更好用的 F 排在第 3，所以到不了 1。若顺序改成 F、D、E、G，NDCG 就是 1。四个都没用则 IDCG 为 0，这个人跳过。

缺 UX 时，只用「用了当 1、没用当 0」，并写明换了口径。

### 5.13 二十个里有没有至少打中一个（Hit@20）

定义：把名单当无顺序的集合，和新使用有交集则为 1，否则为 0，再按人平均。按兴趣算好的那列、以及用户实际拿到的 recommended，各报一次。

为什么要有、作用是什么：不看内部谁先谁后，只问「这 20 个有没有打中」。用来避免第一个兴趣中心占满列表前面时把 R@1 扭歪。和 R@20 的差别是：Hit@20 每个人只贡献 0 或 1；R@20 看罩住了几个，分母是新使用个数。

测的是哪部分能力：集合有没有打中，不管排位。

例子：甲有 D，Hit@20 为 1。乙为 0。

### 5.14 新 skill 率（Novelty）

定义：名单里，取清单之前这个人从未用过的比例。按兴趣算好的那列、以及用户实际拿到的 recommended，各报一次。

为什么要有、作用是什么：采用如果全落在他早就在用的 skill 上，兴趣只是在回放，不是在推荐。Novelty 看名单有没有在给新东西；再和采用对照：新给的有没有被用。

测的是哪部分能力：是在扩展使用，还是在重复旧 skill。

例子：甲的 D、E 取清单前都没用过，Novelty 是 1。若 20 个里 8 个是老 skill，Novelty 是 0.6。

### 5.15 名单里的 skill 彼此有多散（Diversity）

定义：这 20 个 skill 的 description 向量两两之间有多远，再取平均。围着同一个主题会很近；多个兴趣方向铺开应更远。对按兴趣算好的那列算，不要对掺了后面补位的、用户实际拿到的名单算，否则会被质量榜尾部带偏。

为什么要有、作用是什么：一个人可能同时在做部署和写文档。若 20 个全挤在部署，说明多个兴趣方向没有铺开。

测的是哪部分能力：多方向选择有没有铺开，不是准不准。

怎么算：用和线上同一套 description 向量，不要另换一套模型现算。skillhub 用 skillhub 那份向量。可各报一次「只看自研」「只看 skillhub」「整份混在一起」。

### 5.16 不同人的 recommended 有多不像（Jaccard）

定义：两个人名单集合的 Jaccard = 交集 ÷ 并集，再对所有人对平均。越低越说明在因人而异。按兴趣算好的那列、以及用户实际拿到的 recommended，各报一次。用户实际拿到的那份会因为大家都补同一段 UX 尾部而变高，解释时要分开。

为什么要有、作用是什么：和 ranked 的 Jaccard 对照。若按兴趣算好的那列也接近 1，说明大家的兴趣名单几乎一样，兴趣没有起作用。

测的是哪部分能力：recommended 有没有真正因人而异。

例子：甲按兴趣算好的是 D、E，乙是 F、G，Jaccard 是 0。

### 5.17 覆盖了全库多少 skill（Coverage）

定义：所有人按兴趣算好的那列（或用户实际拿到的 recommended，分开报）的并集大小，除以当时能发出去的 skill 总数。自研分母是本仓库已有 main、去掉 retired 和 blocked 的集合；skillhub 分母是当时扫描得到的三方集合。

为什么要有、作用是什么：采用率可以很高，但 20 个永远在围着少数热门转。Coverage 看有没有把长尾 skill 也发过。

测的是哪部分能力：是在扫能下发的 skill 库，还是只围着头部转。

人太少时这个数没有统计意义，写清参与人数。

## 6. 兴趣画得准不准

这些数不看「发出去的 skill 用没用」，避免和采用率绕圈。兴趣在实现里，是把这个人一段段 atom 摘要变成向量，再聚成最多大约 5 个中心。这里问的是：这些中心有没有抓住他接下来在干什么。代码注释里若还写着「用过的 skill 的质心」，那是旧说法，实现已经不是那样。

评的时候必须把 atom 按时间切开：前面一段用来画出中心，后面一段只当探针，不参与画中心。用库里「此刻最新的中心」去对「此刻之后的 atom」也可以，但那不是同一时刻的快照；要评「那天的中心准不准」，应按那天之前的 atom 重画一遍。

### 6.1 后面的 atom，离最近一个兴趣中心有多近（Holdout Cosine）

定义：后面每一个 atom 摘要向量，对各个中心算 cosine，取最大的那个，再对后段取平均。越接近 1 越贴。

为什么要有、作用是什么：这是「兴趣准不准」最直接的数。中心若能代表这个人接下来的事，后段 atom 应该落在某个中心附近。

测的是哪部分能力：兴趣中心有没有抓住后续在干什么，不是 skill 选得对不对。

例子：甲后 3 个 atom 最大 cosine 是 0.82、0.71、0.40，平均约 0.64。

### 6.2 后面有多少 atom 仍然够近（Holdout Near-Rate）

定义：上面那些最大 cosine 里，大于等于写死阈值（例如 0.5）的个数，除以后段 atom 数。阈值写在评测配置里，不要看完数再改。

为什么要有、作用是什么：平均可能被一两个特别近的点拉高。这个数看是普遍贴得住，还是只有少数 atom 很近。

测的是哪部分能力：兴趣中心覆盖后续 atom 的面有多宽。

例子：0.82、0.71 过线，0.40 不过，比例是 2 除以 3。

### 6.3 算出来的中心个数是不是经常只剩 1 个（k Collapse）

定义：中心个数有上限（默认最多 5），atom 少时会自动变少，规则是「最多 5 个，且不超过有摘要的 atom 数除以 3」。看实际得到几个中心，有多少人塌成只有 1 个。

为什么要有、作用是什么：配置了多方向，算出来却经常只剩 1 个，后面 Diversity 就没有来源。

测的是哪部分能力：多方向有没有真的分成多块，不是效果好不好。

### 6.4 同一块内部有多紧，不同块之间有多远（Intra 与 Inter）

定义：前面用来画中心的那些 atom，每个点到自己中心的平均距离是簇内距；中心和中心之间的平均距离是簇间距。簇间距应明显大于簇内距。全文统一用同一种距离（cosine 或欧氏），不要混用。

为什么要有、作用是什么：中心可能是有结构的兴趣，也可能是把噪声切成几块。簇内很松、簇间很近，中心就不可信。

测的是哪部分能力：聚出来的兴趣有没有结构。只有中心不少于 2 个时才报。

另外可用轮廓系数（Silhouette）做附录诊断，样本很少（例如不到 10 个 atom）就不要报。不当主结论。

### 6.5 有多少人根本画不出兴趣（Cold-start Rate）

定义：当时画不出兴趣方向的人数，除以来取过清单的人数。

为什么要有、作用是什么：recommended 里真正按兴趣选的覆盖面有多大。这个比例高，兴趣主表只代表少数人，大多数人实际在用 UX 顶上的 recommended。

测的是哪部分能力：兴趣检索能覆盖多少人，不是准不准。后台更新兴趣之后就可以看，不必等 7 天。

### 6.6 兴趣中心会不会无缘无故跳来跳去（Drift）

定义：同一个人相邻两次 source_revision 画出来的中心，配对之后看平均 cosine。atom 没大变但 cosine 掉很多，就是不稳。

为什么要有、作用是什么：中心乱跳，后面所有「按兴趣选」的效果数都不可信，因为今天按兴趣算好的那列和昨天的可能不是同一套理由。

测的是哪部分能力：兴趣稳不稳。现成库往往只留最新一次中心，评测需要自己留下历史，或按新旧两次 atom 集合各重画一遍。

## 7. 算名单的活跟没跟上（只解释，不当效果分）

这些数一高，上面的采用、排序都不该当成「算法准不准」，因为用户拿到的可能是过期名单，或名义上的 recommended 其实是 UX 顶上或 UX 补位。

待重算积了多少人：兴趣或 skill description 已经变了、按兴趣算好的那列还没重算完的人数。后台跑完一轮后应降下来。看的是更新有没有跟上。

还在把上一份过期名单发出去的比例：标记为过期、但用户来取时仍把上一份成功结果给他的人数，除以库里已经有按兴趣算好的名字的人数。设计上过期也可以先发上一份，避免取清单时卡住；这个比例高，效果回放评的就是旧名单。

整段 UX 顶上的人数占比：取清单时画不出兴趣、或按兴趣算好的那列是空的、于是 recommended 全部用 ranked 接着往下取的人数，除以来取清单的人数。

用户实际拿到的 recommended 里，后面补上的占比：有按兴趣算好的名字，但去掉与 ranked、pinned 重名之后不够填满，用 UX 尾部补上的槽数，除以他实际拿到的 recommended 槽数。看的是用户手里的 20 个有多少其实不是按兴趣选的。

## 8. 第一期先算哪些，其余以后再说

第一期先把「有没有用、20 个有没有多值、兴趣贴不贴得住」算清楚。ranked 用 UX 序重算回放；recommended 用埋点回放，并拆开「按兴趣算好的那列」和「用户实际拿到的那 20 个」。主报这些：

- 两份名单各自的 Adoption（7 天、30 天，按人平均，并按使用次数分层）
- recommended 相对 ranked 的 Incremental Hit（只计按兴趣算好的那列里多出来的）
- 两份名单各自的 Slot Hit
- 三份都没罩住的 OOL（pinned 不算漏）
- 按兴趣算好的那列的 Hit@20，以及 R@5
- 用发出去之前的 atom 画出兴趣，看之后的 atom 的 Holdout Cosine

同一期要带上的切开：Adoption、Incremental Hit、Repeat、UX 按 main 和 staging 分开，并标出自动换侧、prefs 强制指定；recommended 的命中类按 skillhub 和自研分开；整段 UX 顶上、兴趣加 UX 补位、纯兴趣分开报。健康情况（Cold-start Rate、过期名单、整段顶上占比、UX 补位占比）一起出，用来解释主报，不打进「效果好不好」的总分。

Baseline、MAP、NDCG、Diversity、Coverage、Drift，第一期能顺手算就当对照，来不及就标「以后再说」，不要删。

找和这个人兴趣接近的其他人、按 atom 的 tag 去找 skill，也标以后再说。那是另一类能力，不是这 100 个槽发得好不好。

## 9. 实现时对齐现有逻辑（给写脚本的人）

这一节对照 `origin/main` 上现在怎么发清单。

清单由 team server 在用户来取时现拼：blocked 和 retired 先排除；pinned 占位；再按 main 近 30 天 UX 均分（并列 use_count）从本仓库已有 main 的 skill 里切 ranked；再读后台按兴趣提前写好的名字填 recommended。那列里已在 pinned 或 ranked 里的跳过；不够的用 UX 序在剩余名单上往后补。那列为空或没有行，整段 recommended 都走 UX 尾部。还在 baby、没有 main 的 skill 不下发。skillhub 只在补 recommended 时按名字去入口取，side 恒为 main。

那一列名字由后台定时任务写：先更新兴趣（atom 摘要聚成最多约 5 个中心），再按中心依次在向量索引里搜，先填满第一个中心再换下一个，最多留 20 个名字。取清单时不现场做全库计算，也不走引擎里「每中心每轮取 1 个」的那条函数。

有 staging 时，side 不是引擎里那套「staging 先达量再 main 再 pick_side」。普通用户走 CanaryRouter.assign；纳入或生成发起人、用量最多的用户走 auto_canary_side；prefs.side 可覆盖（skillhub 除外）。评测按 side 切开时要带上这些来源。

埋点只写 recommended：`recommendation_log` 的去重键是 `(client_id, skill, side, sha)`。看板总触发率按 `(client, skill)` 取最早时间，且没有按 ranked 和 recommended 切开。ranked 的 Adoption 必须自己重放 UX 序，不要等这张表里出现 ranked。使用事实源是 atom 的 used_skills 和对应的 UX 打分。

评测不要塞进用户取清单的那一次请求里算。取清单要快；评效果是窗口到点之后的只读扫描。
